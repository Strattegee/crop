# CROP: notes for Claude sessions

## Product
Multi-tenant SaaS: first a roster for any employer; agencies plug in through an allocation module and fill shifts employers send them ("Agency fill", ranked agencies, timed escalation). See `docs/decisions/2026-10-25-roster-meeting.md`. Beta tenant: Caring For You (nursing agency, Victoria). Requirement IDs (ROS-, ALC-, CRD-, APP-, NOT-, CLP-, …) come from the CROP MVP Specification: https://claude.ai/artifact/5BSKf7k8EybB9JWnHzLPYt
Build schedule: https://claude.ai/artifact/RtUPeMVpHrJbUZZAms7Dug

## Stack (decided)
- TypeScript modular monolith; pnpm workspaces.
- `apps/web`: Next.js (office and client portal). `apps/api`: NestJS REST API with OpenAPI. `apps/mobile`: React Native (Expo) worker app, iOS + Android, OTA updates, APNs/FCM push.
- PostgreSQL with row-level security on `tenant_id`; Postgres-backed job queue; SSE/WebSockets for live updates.
- Identity provider: Zitadel Cloud, Australian region (decided 22 Oct 2026). OIDC with PKCE; JWT access tokens; 2FA enforced in Zitadel.
- Hosting: DigitalOcean Sydney. Staging = Docker on droplet behind Caddy. Production = managed Postgres + Spaces.

## Data model rules
- Shift requirement, allocation, booking and placement are separate entities.
- Rates and employment are effective-dated.
- Credential requirements are data, not code.
- Store times in UTC plus the facility's IANA timezone.
- Eligibility: hard blocks vs warnings.

## Shift lifecycle
Open → Offered/Broadcast → Booked; Open → Assigned → Booked; Cancelled; Completed → Timesheet (Release 2).

## Repository layout and conventions
- `packages/db`: SQL migrations (`migrations/NNNN_name.sql`, applied in order, never edited after merge), `migrate()`, `createPool()`, `withTenant()`.
- `apps/api`: ES modules (`"type": "module"`); relative imports end in `.js`. Inject providers with explicit `@Inject(TOKEN)` (tests run under Vitest, which doesn't emit decorator metadata). Give `@ApiProperty` an explicit `type`.
- Every tenant-owned table: `tenant_id uuid not null references tenants(id)`, `enable row level security` (not `force`), policy `tenant_id = app_tenant_id()` for using and with check. Add an isolation test. Tables are owned by the migration role, which bypasses RLS (needed for admin tools and security definer functions on managed Postgres, where the owner isn't a superuser); crop_app never owns tables.
- The API connects as `crop_app` (no BYPASSRLS). All tenant data access goes through `withTenant(pool, tenantId, fn)`. Migrations run as the owner role.
- Sign-in: a global `AuthGuard` verifies the Zitadel access token (AUTH_ISSUER, AUTH_AUDIENCE) on every route. Mark exceptions with `@Public()` (no sign-in) or `@NoTenant()` (signed in, no agency). Restrict with `@Roles(...)`; get the agency with `@Tenant()` and the person with `@Auth()`.
- People are platform-level `users` (crop_app can't read the table; it uses `app_user_by_subject`, `app_sign_in`, `app_user_memberships`). Access to an agency is a `membership` with one role: owner, admin, allocator (office), worker, client. Invitations by email are accepted at sign-in only when the identity provider says the email is verified.
- If someone belongs to several agencies, the client sends `x-tenant: <slug>`; the guard checks it is one of theirs.
- Web sign-in (`apps/web`): server-side OIDC code flow with PKCE (`openid-client`), routes `/auth/login`, `/auth/callback`, `/auth/logout` (POST). The access token lives in an encrypted httpOnly cookie (`lib/session.ts`); server components call the API with it via `lib/current-user.ts`. The browser never sees tokens. Env: AUTH_ISSUER, AUTH_CLIENT_ID, AUTH_PROJECT_ID, APP_URL, SESSION_SECRET (32+ chars).
- Requirement levels (migration 0037): `severity` on `credential_requirements` and `shift_duty_requirements` is hard (must have, blocks) / warning (should have) / optional (listed, never checked). `workerCompliance` drops optional rules; `optionalFor()` lists them for the person page (`GET /workers/:id` `optional`); `stepsFromRequirements` leaves them out. UI words: Must have / Should have / Optional (`RuleLevel` in `compliance.ts`).
- Workforce (`apps/api/src/workforce`): workers, credential types, requirement rules, worker credentials with verification and an append-only history (`credential_events`, no UPDATE/DELETE for crop_app). Compliance rules are pure functions in `compliance.ts` (unit-tested); pass a shift date as `onDate` for eligibility (CRD-8). Only verified credentials satisfy hard rules. Editing a verified credential's number, issuer (`issued_by`, migration 0036, `issuedBy` in the API) or dates resets it to unverified. `PATCH` applies the type's number/expiry requirements like adding and records nothing when nothing changed; the person page's Edit (`edit-credential-form.tsx`) sends every field (blank = null).
- Employee card and the person's record (David, 31 Oct; first step of recruitment, backlog item 11): `GET /workers` rows and `GET /workers/:id` carry `card` (`workforce/person-card.ts`: pure `cardFacts` for `held` (verified, not run out, by name), `nextExpiry` (soonest verified credential or visa) and `toCheck`; `cardsFor(db, ids, today)` adds `employmentType`, `contractedHours`, `weekHours` (Monday to Sunday in each site's dates) and `nextShift`). Web: `PersonCard` (`(office)/workers/person-card.tsx`, wording in `lib/person-card.ts`, tested) is the one summary of a person, `compact` in lists and `full` at the top of their page; reuse it wherever a person appears (recruitment board, roster hover). Workers list shows cards by default (`?show=list` for the table). The person's page has tabs in the URL (`?tab=` overview / credentials / rtw / employment / availability / shifts / details; `personTabs` in `lib/person-tabs.ts` flags must-haves to fix). `GET /shifts?workerId=` lists one person's shifts. Who owns each field is still to be decided (David: later).
- Right to work (CRD-6, `right-to-work.controller.ts`): its own record per worker (citizen / NZ citizen / permanent resident / visa holder) with status-specific fields; VEVO required for all non-citizens; visa expiry and hours-per-fortnight limit stored (the limit is for roster eligibility). New details replace the current record (`superseded_at`), history kept. Built into compliance as a hard rule for every worker (`rightToWorkIssue`); it is no longer a generic credential category.
- Documents (`apps/api/src/documents`): credential evidence in DigitalOcean Spaces (Sydney) via the `DocumentStore` interface (`MemoryStore` in tests and local dev). Uploads go through the API (10 MB, type checked from the file's bytes: PDF, JPEG, PNG, HEIC); storage keys contain no names; files open via 5-minute signed links; removal marks the row removed and keeps the object.
- Notifications (`apps/api/src/notifications`): queue a message with `queueNotification(db, tenantId, …)` inside `withTenant`; the `NotificationDispatcher` loop (Postgres queue, `app_claim_notifications`/`app_finish_notification`) sends it with retries (60s, 5m, 15m, 1h). Email: Resend (`EmailSender`); SMS: ClickSend (`SmsSender`), Australian mobiles only, monthly cap per agency (`tenant_settings.sms_monthly_cap`). Use a `dedupeKey` for anything that must only go once (reminders). When real email is on (RESEND_API_KEY), email to reserved example domains (demo people, `isExampleAddress`) is logged as skipped, not sent. Never put health information or document numbers in a message (vaccinations are "a vaccination record"); link to CROP for detail. Expiry reminders (`reminders.ts`, CRD-7): hourly, from 8am agency time; workers at 60/30/7 days (SMS only at 7), the office's dates (30 days, expiry day, expired; People and Equipment sections: current `equipment_checks` of non-retired equipment, plus how many upcoming bookings fall after the date; renewed credentials skipped) go in the daily dashboard email (below) to Compliance and Overview people (owners/admins when nobody has those); `reminder_marks` records what has been sent, marked only when a fresh email carried it. Tests run with NOTIFY_DISPATCH=off and call `runOnce()`.

- Roster (`apps/api/src/roster`, migration 0009): `employment_terms` (effective-dated: a new term ends the previous one the day before; migration 0032: a mistaken row is never edited or deleted but marked `withdrawn_at`/`withdrawn_reason` corrected|withdrawn, a correction inserts a new row with `replaces_id`; every query on `employment_terms` must add `withdrawn_at is null`; migration 0033: end of employment = the latest live term's `ends_on` plus `end_reason`/`ended_by`/`ended_at` (`POST /workers/:id/employment/end {lastDay, reason}` returns `shiftsAfter`; `…/end/undo` is a correction); eligibility gets live terms (`employmentReason`: after an end or in a gap = hard block `employment`, before the first terms = warning, no terms = nothing); lists of people use `EMPLOYED_ON(date)` from `eligibility-data.ts` so leavers drop off; `POST /workers/:id/employment/:termsId/correct|withdraw`, rules in `roster/employment.ts`; no DELETE for crop_app), `shift_codes` (business-wide or per site, local times), `shifts` (one position each; times stored UTC, created from the site's local date and time; overnight when end < start), `shift_assignments` (who fills it; `resource_kind` is ready for equipment). Assigning locks the shift and the worker rows and refuses overlapping assignments (hard block). `GET /roster?from&to` returns shifts plus each active worker's terms and rostered hours.
- Eligibility (`roster/eligibility.ts`, pure; data in `eligibility-data.ts`): assigning is refused for the wrong role, a hard credential rule or right to work not met on the shift's local date, double booking, or a limited visa going over its hours in any 14 days starting on a Monday; warnings for expiring credentials, warning-level rules and rest under `tenant_settings.min_rest_hours`. `GET /shifts/:id/candidates` lists everyone active with blocks and warnings (ready first, then fewest hours that week). - Equipment (`roster/equipment.controller.ts`, rules in `roster/equipment.ts`, migration 0011): `equipment_types` (optional `operator_credential_type_id`), `equipment` (active / out_of_service / retired), `equipment_checks` (dates that must be current, by name; a new one supersedes the current one). Equipment goes on a shift as a `shift_assignments` row with `resource_kind = 'equipment'` (status `confirmed`); a shift has at most one person and any number of equipment items, and shift status still follows the person. Booking locks the shift and the equipment rows. Hard blocks: not active, a date overdue on the shift's local date, overlapping booking, the person on the shift lacking a verified, current operator credential (also checked when assigning a person, via `operatorNeedsForShift`). Equipment-only shifts (migration 0012, `shifts.needs_person = false`, API `equipmentOnly`; role defaults to "Equipment only"): for dry hire; nobody can be assigned, no operator rule, status follows the equipment (booked while anything is on it). - Items (`apps/api/src/items`, rules in `items.ts`, migration 0013): `items` catalogue (category, unit, `unit_cost_cents`, optional `charge_cents` to the client, `tracks_stock`, `reorder_level`) and `stock_movements`, an append-only ledger (no UPDATE/DELETE for crop_app; kinds received / issued (to a person, optional shift) / used (on a shift) / returned / adjusted). On hand per site = sum of the site's movements; lock the item row before any movement. Quantities numeric(12,3), money in integer cents; each movement copies the cost and charge, so price changes never rewrite history. Corrections are new rows (return or stocktake), never edits. Transfers (migration 0031, `POST /items/:id/transfer {fromFacilityId, toFacilityId, quantity}`): kind `transferred`, two rows (minus and plus) sharing `transfer_id`, counted items only; usage reports ignore them. `GET /shifts/:id/items` and `GET /workers/:id/items` give net use with cost and charge; `?byPerson=true` on the shift one splits lines by holder (`workerId`/`workerName`, null = used on the shift), which the roster's shift panel uses for its Items section (add with `POST /items/:id/issue {shiftId, workerId?}`, return per line). The Roster tab (`src/RosterTab.tsx`, helpers in `src/roster.ts`) reads `GET /shifts?from&to&facilityId` and `GET /roster/weeks`, publishes with `POST /roster/publish` (`publishLabel` matches the web's button); its week/day/site (`RosterView`) lives in `ManagerHome` so opening a shift doesn't lose it. Business words for other terms: `termWord(terms, key, one, many)`. The covering line (`coveringChoices`, `canSetCovering` in `src/shift.ts`, same ordering as the web's) reads people and leave from `GET /roster` for the shift's date and saves with `PUT /shifts/:id/covering`; hidden while `changeRefusal` applies. Today tab starts with "Your <focus> numbers" (`GET /dashboard`, one swipeable row, off target first; `kpiValue`, `kpiNote`, `kpiOrder` in `src/manager.ts`).
- Legal documents (David's draft pack v0.1, 29 Oct): sources in `docs/legal/*.md` (the original .docx kept beside them; `launch-checklist.md` is internal and not published). `python3 docs/legal/build.py` regenerates `apps/web/lib/legal/documents.ts`; public pages `/legal` and `/legal/[slug]` (privacy, worker-notice, terms, data-processing, acceptable-use, schedules) render them with `lib/legal/markdown.ts` (plain data, never injected HTML) and highlight bracketed gaps still to fill. Public pages carry `LegalFooter`. When a feature changes what personal information CROP holds or who processes it (new data, a new outside service), update the privacy policy, DPA data categories and Schedule D in the same pull request and tell David.
- Dates like "today" come from the business's time zone (`todayIn(settings.timezone)`), never the server's UTC date. In the web: `businessZone()`, `todayIn(zone)` and `whenIn(zone)` from `lib/business.ts` (settings fetched once per request); never hard-code Australia/Melbourne in new screens.

## Local development
```sh
pnpm install
docker compose up -d                       # Postgres on 5432 (or use a local Postgres 16)
cp .env.example .env
DATABASE_URL=postgres://crop:crop@localhost:5432/crop APP_DB_PASSWORD=crop_app pnpm db:migrate
pnpm --filter @crop/db build
pnpm dev                                   # API :4000 (docs at /docs), web :3000
pnpm --filter @crop/mobile start           # Expo; scan the QR code with Expo Go
```
Checks before a PR: `pnpm typecheck && pnpm test && pnpm build`.
