# CROP: notes for Claude sessions

## Product
Multi-tenant SaaS: first a roster for any employer; agencies plug in through an allocation module and fill shifts employers send them ("Agency fill", ranked agencies, timed escalation). See `docs/decisions/2026-10-25-roster-meeting.md`. Beta tenant: Caring For You (nursing agency, Victoria). Requirement IDs (ROS-, ALC-, CRD-, APP-, NOT-, CLP-, …) come from the CROP MVP Specification: https://claude.ai/artifact/5BSKf7k8EybB9JWnHzLPYt
Build schedule: https://claude.ai/artifact/RtUPeMVpHrJbUZZAms7Dug

## Stack (decided)
- TypeScript modular monolith; pnpm workspaces.
- `apps/web`: Next.js (office and client portal). `apps/api`: NestJS REST API with OpenAPI. `apps/mobile`: React Native (Expo) worker app, iOS + Android, OTA updates, APNs/FCM push.
- PostgreSQL with row-level security on `tenant_id`; Postgres-backed job queue; SSE/WebSockets for live updates.
- Identity provider: Zitadel Cloud, Australian region (decided 22 Oct 2026). OIDC with PKCE; JWT access tokens; 2FA enforced in Zitadel.
- Hosting: DigitalOcean Sydney. Staging = Docker on droplet behind Caddy. Production = managed Postgres + Spaces.

## Data model rules
- Shift requirement, allocation, booking and placement are separate entities.
- Rates and employment are effective-dated.
- Credential requirements are data, not code.
- Store times in UTC plus the facility's IANA timezone.
- Eligibility: hard blocks vs warnings.

## Shift lifecycle
Open → Offered/Broadcast → Booked; Open → Assigned → Booked; Cancelled; Completed → Timesheet (Release 2).

## Repository layout and conventions
- `packages/db`: SQL migrations (`migrations/NNNN_name.sql`, applied in order, never edited after merge), `migrate()`, `createPool()`, `withTenant()`.
- `apps/api`: ES modules (`"type": "module"`); relative imports end in `.js`. Inject providers with explicit `@Inject(TOKEN)` (tests run under Vitest, which doesn't emit decorator metadata). Give `@ApiProperty` an explicit `type`.
- Every tenant-owned table: `tenant_id uuid not null references tenants(id)`, `enable row level security` (not `force`), policy `tenant_id = app_tenant_id()` for using and with check. Add an isolation test. Tables are owned by the migration role, which bypasses RLS (needed for admin tools and security definer functions on managed Postgres, where the owner isn't a superuser); crop_app never owns tables.
- The API connects as `crop_app` (no BYPASSRLS). All tenant data access goes through `withTenant(pool, tenantId, fn)`. Migrations run as the owner role.
- Sign-in: a global `AuthGuard` verifies the Zitadel access token (AUTH_ISSUER, AUTH_AUDIENCE) on every route. Mark exceptions with `@Public()` (no sign-in) or `@NoTenant()` (signed in, no agency). Restrict with `@Roles(...)`; get the agency with `@Tenant()` and the person with `@Auth()`.
- People are platform-level `users` (crop_app can't read the table; it uses `app_user_by_subject`, `app_sign_in`, `app_user_memberships`). Access to an agency is a `membership` with one role: owner, admin, allocator (office), worker, client. Invitations by email are accepted at sign-in only when the identity provider says the email is verified.
- If someone belongs to several agencies, the client sends `x-tenant: <slug>`; the guard checks it is one of theirs.
- Web sign-in (`apps/web`): server-side OIDC code flow with PKCE (`openid-client`), routes `/auth/login`, `/auth/callback`, `/auth/logout` (POST). The access token lives in an encrypted httpOnly cookie (`lib/session.ts`); server components call the API with it via `lib/current-user.ts`. The browser never sees tokens. Env: AUTH_ISSUER, AUTH_CLIENT_ID, AUTH_PROJECT_ID, APP_URL, SESSION_SECRET (32+ chars).
- Workforce (`apps/api/src/workforce`): workers, credential types, requirement rules, worker credentials with verification and an append-only history (`credential_events`, no UPDATE/DELETE for crop_app). Compliance rules are pure functions in `compliance.ts` (unit-tested); pass a shift date as `onDate` for eligibility (CRD-8). Only verified credentials satisfy hard rules. Editing a verified credential's number or dates resets it to unverified.
- Right to work (CRD-6, `right-to-work.controller.ts`): its own record per worker (citizen / NZ citizen / permanent resident / visa holder) with status-specific fields; VEVO required for all non-citizens; visa expiry and hours-per-fortnight limit stored (the limit is for roster eligibility). New details replace the current record (`superseded_at`), history kept. Built into compliance as a hard rule for every worker (`rightToWorkIssue`); it is no longer a generic credential category.
- Documents (`apps/api/src/documents`): credential evidence in DigitalOcean Spaces (Sydney) via the `DocumentStore` interface (`MemoryStore` in tests and local dev). Uploads go through the API (10 MB, type checked from the file's bytes: PDF, JPEG, PNG, HEIC); storage keys contain no names; files open via 5-minute signed links; removal marks the row removed and keeps the object.
- Notifications (`apps/api/src/notifications`): queue a message with `queueNotification(db, tenantId, …)` inside `withTenant`; the `NotificationDispatcher` loop (Postgres queue, `app_claim_notifications`/`app_finish_notification`) sends it with retries (60s, 5m, 15m, 1h). Email: Resend (`EmailSender`); SMS: ClickSend (`SmsSender`), Australian mobiles only, monthly cap per agency (`tenant_settings.sms_monthly_cap`). Use a `dedupeKey` for anything that must only go once (reminders). When real email is on (RESEND_API_KEY), email to reserved example domains (demo people, `isExampleAddress`) is logged as skipped, not sent. Never put health information or document numbers in a message (vaccinations are "a vaccination record"); link to CROP for detail. Expiry reminders (`reminders.ts`, CRD-7): hourly, from 8am agency time; workers at 60/30/7 days (SMS only at 7), office owners/admins one daily digest (30 days, expiry day, expired), with a People and an Equipment section (current `equipment_checks` of non-retired equipment, plus how many upcoming bookings fall after the date); renewed credentials skipped; `reminder_marks` records what the digest has covered. Tests run with NOTIFY_DISPATCH=off and call `runOnce()`.
- Shift types (Steve's word; table and API are `shift_codes`, migration 0021 adds `letter`, 1–3 capitals or digits): web `(office)/settings/shift-types` (function code 9100, a sub-page so not in the menu: `subPage: true` in `FUNCTIONS`). `PATCH /shift-codes/:id` changes name, letter (blank clears), times, break, active; shifts already created keep their copied times. Roster cards show `shiftLetter`, else A/P/N from the start time. Call them "shift types" in the UI.
- Roster (`apps/api/src/roster`, migration 0009): `employment_terms` (effective-dated: a new term ends the previous one the day before; migration 0032: a mistaken row is never edited or deleted but marked `withdrawn_at`/`withdrawn_reason` corrected|withdrawn, a correction inserts a new row with `replaces_id`; every query on `employment_terms` must add `withdrawn_at is null`; migration 0033: end of employment = the latest live term's `ends_on` plus `end_reason`/`ended_by`/`ended_at` (`POST /workers/:id/employment/end {lastDay, reason}` returns `shiftsAfter`; `…/end/undo` is a correction); eligibility gets live terms (`employmentReason`: after an end or in a gap = hard block `employment`, before the first terms = warning, no terms = nothing); lists of people use `EMPLOYED_ON(date)` from `eligibility-data.ts` so leavers drop off; `POST /workers/:id/employment/:termsId/correct|withdraw`, rules in `roster/employment.ts`; no DELETE for crop_app), `shift_codes` (business-wide or per site, local times), `shifts` (one position each; times stored UTC, created from the site's local date and time; overnight when end < start), `shift_assignments` (who fills it; `resource_kind` is ready for equipment). Shift status follows the assignment: open → assigned → booked (confirmed); cancelling removes the assignment. Assigning locks the shift and the worker rows and refuses overlapping assignments (hard block). `GET /roster?from&to` returns shifts plus each active worker's terms and rostered hours.
- Eligibility (`roster/eligibility.ts`, pure; data in `eligibility-data.ts`): assigning is refused for the wrong role, a hard credential rule or right to work not met on the shift's local date, double booking, or a limited visa going over its hours in any 14 days starting on a Monday; warnings for expiring credentials, warning-level rules and rest under `tenant_settings.min_rest_hours`. `GET /shifts/:id/candidates` lists everyone active with blocks and warnings (ready first, then fewest hours that week). Reuse `eligibilityForShift` for bank fill and agency allocation.
- Equipment (`roster/equipment.controller.ts`, rules in `roster/equipment.ts`, migration 0011): `equipment_types` (optional `operator_credential_type_id`), `equipment` (active / out_of_service / retired), `equipment_checks` (dates that must be current, by name; a new one supersedes the current one). Equipment goes on a shift as a `shift_assignments` row with `resource_kind = 'equipment'` (status `confirmed`); a shift has at most one person and any number of equipment items, and shift status still follows the person. Booking locks the shift and the equipment rows. Hard blocks: not active, a date overdue on the shift's local date, overlapping booking, the person on the shift lacking a verified, current operator credential (also checked when assigning a person, via `operatorNeedsForShift`). Equipment-only shifts (migration 0012, `shifts.needs_person = false`, API `equipmentOnly`; role defaults to "Equipment only"): for dry hire; nobody can be assigned, no operator rule, status follows the equipment (booked while anything is on it). Bank fill, agency fill and needs-attention must skip them for people. Shifts include `equipmentOnly` and `equipment: [{id, name, typeName}]`; `GET /roster` adds `equipment` rows with `bookedHours`.
- Items (`apps/api/src/items`, rules in `items.ts`, migration 0013): `items` catalogue (category, unit, `unit_cost_cents`, optional `charge_cents` to the client, `tracks_stock`, `reorder_level`) and `stock_movements`, an append-only ledger (no UPDATE/DELETE for crop_app; kinds received / issued (to a person, optional shift) / used (on a shift) / returned / adjusted). On hand per site = sum of the site's movements; lock the item row before any movement. Quantities numeric(12,3), money in integer cents; each movement copies the cost and charge, so price changes never rewrite history. Corrections are new rows (return or stocktake), never edits. Transfers (migration 0031, `POST /items/:id/transfer {fromFacilityId, toFacilityId, quantity}`): kind `transferred`, two rows (minus and plus) sharing `transfer_id`, counted items only; usage reports ignore them. `GET /shifts/:id/items` and `GET /workers/:id/items` give net use with cost and charge; `?byPerson=true` on the shift one splits lines by holder (`workerId`/`workerName`, null = used on the shift), which the roster's shift panel uses for its Items section (add with `POST /items/:id/issue {shiftId, workerId?}`, return per line). Items aren't shift changes, so that section shows on live weeks too.
- Bank fill (`roster/bank-fill.controller.ts`, helpers and message wording in `roster/bank-fill.ts`, migration 0014): `shift_offers` (pending / accepted / declined / withdrawn / filled; optional `expires_at`, shown as `expired` once past; no DELETE for crop_app). `GET /shifts/:id/bank-fill` (bank and casual staff by default, `everyone=true` for all), `POST /shifts/:id/offers` (everyone must be eligible; email and SMS unless `notify: false`), `POST /offers/:id/accept|decline` (the office records a reply), `POST /shifts/:id/offers/withdraw`. Accepting locks the shift, then the offer, then the worker, re-checks eligibility and books (confirmed); the other pending offers close as filled. Accept/decline logic lives in `roster/offer-replies.ts` (shared by the office and links). Offer links (migration 0016, `offer-links.controller.ts`, web `/offer/[token]`): when APP_URL is set, each offer message carries a one-off link (32 random bytes, base64url; only the SHA-256 is stored in `shift_offers.link_hash`); `@Public()` `GET /offer-links/:token` (never changes anything), `POST …/accept|decline`; the tenant is found with the security definer `app_offer_by_link(hash)` and everything else goes through `withTenant`. Link responses show the first name and the shift only, and plain reasons (never credential details). `responded_via` is office or link. Assigning directly closes pending offers as filled and cancelling as withdrawn (`closePendingOffers` in `roster/offers-data.ts`).
- Availability and leave (`roster/availability.controller.ts`, rules in `roster/availability.ts`, migration 0018): `availability_patterns` (weekly, ISO weekday → periods am/pm/night; empty = not that day; missing = nothing said), `availability_dates` (one date, replaces the pattern that day), `leave_records` (whole days, kinds annual/personal/long_service/unpaid/other, requested → approved/declined, requested or approved → cancelled; no DELETE for crop_app). A shift's period comes from its local start time (AM 05:00–11:59, PM 12:00–18:59, night otherwise). In eligibility, approved leave on the shift's local start date is a hard block (`leave`); requested leave and not available are warnings (`availability`); candidates carry `available` and rank free people first. Never say the leave kind in reasons or messages. Owners/admins approve; allocators record requests. `GET /roster` includes `leave`. Office screens: an "Availability and leave" card on the person's page (`workers/[id]/availability-card.tsx`: usual week as one choice per day, date changes, record leave) and the Leave page (`(office)/leave`, function code 3200: approve/decline requests, cancel approved leave). Recording or approving tells the office how many of the person's shifts need cover.
- Roster screen (`apps/web/app/(office)/roster`): server-rendered; state lives in the URL (`week` = Monday, or `span=day|month` with `date`; `site`, `view` = area|person, `shift` = selected; date maths and the day timeline are pure helpers in `roster/view.ts`, tested in `apps/web/test`). Day view fetches the whole week so hours compare with weekly contracts; month view is a calendar of daily totals with no strip or panel, and every form posts `back` so actions return to the same view. Down the left, the ribbon strip (`roster/strip.tsx`, client): People / Equipment / Items tabs, each person's type (F/P/B/C), hours and balance against contract, marked ready/warning/blocked for the selected shift; drag a person onto an open shift or equipment onto any shift (`dropOnShift`). Each card carries the ribbon, Steve's colour for the shift's stage (decided 26 Oct, `stage()` in the roster page): grey unfilled, pale yellow offered (`offersPending`), darker yellow allocated (assigned, waiting for them), pink accepted (reserved for approve-first, not used yet), purple pulled out (`pulledOutName`: unassign with `pulledOut: true`, migration 0020 `shift_assignments.removed_reason`), green booked, red cancelled (`GET /roster?cancelled=true`). Cards start with A/P/N from the local start time (same periods as availability), person rows show leave lines ("On leave" / "Leave requested", never the kind), and a Day totals row sums filled hours. Don't call a shift code OPEN (it reads as the stage). Cards / Detailed / Simple (`look` = detailed|simple in the URL, week view only since day bars have a fixed height; `parseLook`, `detailLines`, `simpleLine` in `roster/view.ts`). Data from `GET /roster`, the side panel from `/shifts/:id/bank-fill`, `/candidates` and `/equipment-candidates`.
- Publishing (Draft → Live → History, migration 0022, `roster/publishing.ts` pure rules, `publishing.controller.ts`): `roster_publications` (per site and week, `week_start` a Monday, versions; append-only) and `shift_changes` (append-only log written by triggers on `shifts` and `shift_assignments`, so every path is logged; `after_publish` marks changes to a published week). Who made a change comes from `withTenant(pool, tenantId, fn, actor)` (sets `app.actor_id/name/via`; use `actorOf(auth)` in office endpoints, `{ via: 'link' }` for reply links); new endpoints that change shifts must pass an actor. A week is history once it is over in the site's time zone (published or not) and can't be published; publishing again needs a change since. `GET /roster/weeks`, `POST /roster/publish` (one site or all), `GET /roster/changes`, `GET /shifts/:id/history`; summaries in plain words (`changeSummary`). Publishing tells staff (David and Steve, 27 Oct): the first publication emails and texts everyone on the site's week their shifts; publishing again (after changes) tells only the people whose shifts changed since, including anyone taken off (`tellStaff` in `publishing.controller.ts`, wording `rosterMessage`, template `roster_published`, dedupe per version and person). `notify: false` publishes without messages (the roster's "Tell staff" tick box). Roster screen: status bar with Publish week / Publish N changes, `log=1` shows the week's changes, the shift panel has History. After publishing (migration 0024): `tenant_settings.published_changes` = open | managers (owners/admins only) | locked; enforced in `app_log_shift_change` via `app_roster_change_refusal(facility, week)`, which reads `app.actor_role`/`app.actor_via` (`Actor.role`, set by `actorOf`); link replies pass unless locked, no-actor (system) changes always pass. It raises SQLSTATE `CRLK1`, which the global `DbRulesInterceptor` turns into a 409 with the message. Anything that leads to a shift change without changing it yet (offers) checks `rosterChangeRefusal(db, shiftId)` first. Change requests (migration 0025, `roster/change-requests.ts` pure, `change-requests.controller.ts`): `roster_change_requests` (kinds assign / confirm / remove / pulled_out / cancel / other; pending → approved / declined / withdrawn; one pending per shift; no DELETE). `POST /shifts/:id/change-requests` only when `rosterChangeRefusal` refuses the asker; `GET /roster/change-requests?weekStart` (pending by default, rows carry `summary`, `canDecide`, `canWithdraw`); owners/admins `POST /change-requests/:id/approve|decline`, the asker or an owner/admin `…/withdraw`. Approving makes the change with the approver as actor through the shared functions in `roster/shift-actions.ts` (`assignWorker`, `confirmWorker`, `removeWorker`, `cancelShift`, also used by the shift endpoints); if it fails nothing changes. Emails (migration 0026 copies the asker's sign-in email to `requested_by_email`): a new request emails every owner/admin except the asker (`app_agency_office_emails()`, template `change_request`), and approve/decline/withdraw by someone else emails the asker (`change_request_decided`); wording in `requestArrivedEmail`/`requestDecidedEmail`, worded against the shift before it changes, with a roster link when APP_URL is set. `GET /roster/weeks` rows carry `changeRefusal` (for the person asking) and `pendingRequests`.
- Roster templates (migration 0023, `roster/templates.ts` pure rules, `templates.controller.ts`): `roster_templates` (per site, unique live name, `archived_at` instead of delete) and `roster_template_shifts` (weekday 1–7, local start/end, break, area, role, shift type, `needs_person`, optional usual `worker_id`; append-only). `POST /roster/templates` saves a site's week (cancelled shifts left out; `people: false` drops the people), `POST /roster/templates/:id/apply` and `POST /roster/copy-week` (`fromWeek` defaults to the week before) create ordinary shifts at the same local times and assign the usual person only when `eligibilityForShift` passes (status assigned); the rest stay open and come back in `leftOpen` with the reason, plus a plain `summary`. Refused for a week that is over, or one that already has shifts unless `addToExisting`. Equipment (migration 0027 `roster_template_equipment`, append-only): saved with the template unless `equipment: false`; applying and copying book it again after the person (so the operator rule sees them) only when `equipmentForShift` passes, otherwise it comes back in `equipmentLeftOff` with the reason; `equipment: false` skips it. `POST /roster/copy-weeks` (`fromWeek`, `weeks` 1–6, `toWeek` defaulting to straight after; pairs from `weekPairs`, overlaps refused) copies a run of weeks, all or nothing: every target week is checked before anything is created; empty source weeks come back in `emptyWeeks`; summary from `copyWeeksSummary`. The month view's "Copy this month" card uses it with the Mondays in the month (`monthCopyWeeks` in `roster/view.ts`). Roster screen: "Templates and copying" card (week and day views); `attempt()` takes a function for a success message worked out after the call.
- Shift duties (migration 0029, `roster/duties.controller.ts`, web `(office)/settings/shift-duties`, function code 9110): `shift_duties` (name unique per business, `active`; no DELETE), `shift_duty_requirements` (duty → credential type, hard/warning; replaced as a set), `shift_duty_links` (duties on a shift; insert/delete logged by trigger as `duty_added`/`duty_removed`, so the after-publishing rule applies), `roster_template_duties`. `PUT /shifts/:id/duties {dutyIds}` returns the shift plus `personProblems`. `dutyRulesForShift` feeds `ctx.evaluate(..., extraRules)` inside `eligibilityForShift`, so every path (assign, offers, templates, attention) sees them; issues carry `forDuty` and reasons end "(needed for <duty>)". Shifts include `duties: [{id, name}]`. Templates and copying add duties before the usual person. `POST /shifts` takes `dutyIds` (active duties, put on every shift created). Industry packs carry `duties` (name, description, must/should), added only when no duty of that name exists; a duty shared by packs must be described identically (tested).
- Cover rules (migration 0030, `roster/cover.ts` pure, `cover-data.ts`, `cover-rules.controller.ts`, web `(office)/settings/cover-rules`, function code 9120): `site_cover_rules` (credential type, one site or every site when `facility_id` is null; `active`, no DELETE). Met by the people on shift together (assigned or confirmed, verified credential current on the shift's local date: `holdsOn`), so never a block: `coverGaps` finds times someone is working but no holder is; `GET /roster/cover-gaps?from&to` (local dates, up to 62 days) for the roster's "cover gaps" card (day and week views), and Needs attention adds `cover_gap` items (ranked after blocked, before open; a gap under way stays until it ends). Owners/admins `POST /cover-rules` (re-adding a switched-off rule switches it on), `PATCH /cover-rules/:id {active}`.
- Needs attention (`roster/attention.ts` pure rules and wording, `attention.controller.ts`): `GET /roster/attention?facilityId&days` (default 7, 1–14, from now) lists shifts starting soon that need the office: `open` (nobody on it, with what's been offered; equipment-only shifts with nothing booked), `unconfirmed` (assigned, not confirmed), `person_blocked` (hard blocks from `eligibilityForShift` for the person on it) and `equipment_blocked` (from `equipmentForShift`); `urgent` within 24 hours; urgent first, then blocked, open, unconfirmed, then start time. Rows carry `title`, `detail`, `startsIn` and the shift; the response has `total`, `urgent` and `byKind` counts. The Dashboard (`(office)/dashboard`) shows the same list (top five) with leave requests (`GET /leave?status=requested`) and pending change requests (`GET /roster/change-requests` with no `weekStart` = pending in every week). Shown as the Needs attention panel on the roster (`roster/attention-panel.tsx`): open when anything is urgent unless the office closed it; the choice is kept in the `crop_attention` cookie (constant in `roster/view.ts`: a server component can't import plain values from a `'use client'` file). Leave reasons come from eligibility, so never the leave kind.
- Equipment and items screens (`(office)/equipment`, `equipment/[id]`, `(office)/items`; function codes 5000 and 5500, named with the business's words): the register with dates and their state, add equipment and types, status, dates that must stay current (a new one replaces the old), upcoming bookings; items with cost, charge and stock per site, receive, issue to a person, stocktake, low stock warning.
- Industry templates (`apps/api/src/industry/packs.ts`, data only; `industry.controller.ts`, migration 0015): `GET /industry-packs`, `GET /industry-packs/:id`, `POST /industry-packs/:id/apply` (owner/admin) adds what's missing, matched by name or code, never overwriting (credential types, `business_roles`, role rules must=hard/should=warning, business-wide shift codes, equipment types with operator credential, items); applications recorded in `industry_pack_applications`. Shared credentials must be described identically across packs (tested). `GET/POST /roles` = the business's role list. Templates are starting points, not legal advice.
- Words and codes (`docs/CODES.md`, migration 0017): every concept has a fixed term code (1010 worker … 1090 agency, `apps/api/src/terms/terms.ts`) and every screen a function code (`apps/web/lib/functions.ts`). Users never see codes. Each business has one set of words (`business_terms`; GET /terms for any member, PUT /terms owner/admin; blank resets); the first industry template applied suggests them. In the web, `const tw = await words()` then `tw.one(T.worker)` / `tw.many(T.site)`; never hard-code a renamable word in new screens.
- Platform administration (migration 0019, `apps/api/src/platform`, web `(office)/platform`, function code 9900): Strattegee staff add businesses and give, change or remove people's access. Platform admins are in `platform_admins`, granted only by the owner-run tool (`invite-cli --role platform-admin`, also a choice in the "Invite someone to staging" workflow); the app can never grant it. crop_app reaches it only through security definer functions that check the caller first (`app_platform_*`), and every change goes into `platform_admin_events`. Access goes straight to an account only if its email is verified (`users.email_verified`, set at sign-in); otherwise it's an invitation accepted at the first verified sign-in. The guard refreshes sign-in when an invitation is waiting (`app_user_has_invite`), so people pick up a new business without signing out. A business always keeps at least one owner. `GET /me` has `platformAdmin`. Giving access (or adding a business with an owner) queues a welcome email (`welcomeEmail`, template `welcome`) in that business's message log; pass `welcome: false` to skip.
- Staging demo tools (`DEMO_TOOLS=on` on the web container only): café demo on an empty roster (`roster/demo-cafe.ts`), "Add demo staff" per applied template, "Complete demo staff credentials" and "Fill open shifts with demo staff" (`(office)/demo-tools.ts`). They only ever touch invented people with `@example.com` emails.
- Countries (migration 0028, `apps/api/src/common/countries.ts`, web `lib/places.ts` + `lib/place-fields.tsx`): CROP supports AU, NZ, US, GB (in that order, David and Steve 27 Oct). `tenant_settings.country` is the business's country (default for new sites); `facilities.country` with region and postcode checked per country (AU/US state lists, NZ/GB free text; AU/NZ 4-digit, US ZIP, UK postcode tidied to `LS1 1UR`). A site's time zone: the one given, else from the state (`zoneFor`), else the country's default (`siteZone`). Any IANA zone in the country's list can be chosen; shift times are UTC plus the site's zone, so no other code changes. Never assume Australia in new code: use the site's or business's country.

```sh
pnpm install
docker compose up -d                       # Postgres on 5432 (or use a local Postgres 16)
cp .env.example .env
DATABASE_URL=postgres://crop:crop@localhost:5432/crop APP_DB_PASSWORD=crop_app pnpm db:migrate
pnpm --filter @crop/db build
pnpm dev                                   # API :4000 (docs at /docs), web :3000
pnpm --filter @crop/mobile start           # Expo; scan the QR code with Expo Go
```
Checks before a PR: `pnpm typecheck && pnpm test && pnpm build`.

## Deployment
Merges to `main` deploy to https://staging.cropwms.com (see `deploy/staging/README.md`).
